## 1. Overall purpose and architecture

The `trading_bot` repository is a Python-based system designed to backtest algorithmic trading strategies on historical market data, primarily focusing on the Nifty 50 index constituents [cite:file=src/backtest/config_reader.py;symbol=backtest;lines=127-127]. It solves the problem of evaluating the performance of various technical analysis patterns, such as candlestick reversals and mean reversion signals, by simulating their execution over specific date ranges [cite:file=src/backtest/engine.py;symbol=signals;lines=275-275] [cite:file=src/backtest/config_reader.py;symbol=execution;lines=131-131]. The primary users are quantitative analysts or developers seeking to validate strategy logic before live deployment [cite:file=src/risk/risk_engine.py;symbol=RiskEngine.validate;lines=16-27]. The tech stack relies on Python, utilizing `pandas` for data manipulation, `yfinance` for potential data acquisition, `pyyaml` for configuration management, and `pytest` for unit testing [cite:file=tests/test_bullish_marubozu.py;symbol=TestBullishMarubozuStrategy;lines=13-154] [cite:file=run_backtest.py;symbol=main;lines=24-93] [cite:file=src/backtest/config_reader.py;symbol=load_backtest_config;lines=155-212]. The repository is organized into distinct layers: a `src` directory containing the core logic for data access, strategy implementation, and backtest execution; a `configs` folder holding YAML files that define specific strategy parameters; a `data` directory storing local CSV files for OHLCV candle data; and top-level Python scripts that serve as entry points for running individual backtests or comparative studies [cite:file=run_backtest.py;symbol=main;lines=24-93] [cite:file=src/data/market_data.py;symbol=CSVDataSource;lines=439-666] [cite:file=run_position_study.py;symbol=results;lines=59-59].

## 2. Key components/modules

*   **`src/backtest`**: This module orchestrates the simulation and reporting [cite:file=src/backtest/config_reader.py;symbol=backtest;lines=127-127]. The `BacktestEngine` class manages the core loop, processing buy and sell signals while handling concurrent positions, stop-losses, and equity updates for each candle [cite:file=src/backtest/engine.py;symbol=BacktestEngine;lines=129-620]. The `load_backtest_config` function in `config_reader.py` validates and parses YAML files into a `BacktestConfig` object, ensuring all components are resolved before execution [cite:file=src/backtest/config_reader.py;symbol=path;lines=169-169] [cite:file=src/backtest/config_reader.py;symbol=load_backtest_config;lines=155-212]. The `result_printer` module analyzes output, with `_parse_csv_result` extracting summary fields like total return and maximum drawdown from CSV files, and the `strategy` function formatting these metrics for final reporting [cite:file=src/backtest/result_printer.py;symbol=strategy;lines=167-167] [cite:file=src/backtest/result_printer.py;symbol=_parse_csv_result;lines=92-117].
*   **`src/strategy`**: This package contains the trading logic, utilizing the Strategy Pattern where classes like `BullishTrendContinuationStrategy` implement a common interface defined by the base `Strategy` class [cite:file=src/strategy/strategy.py;symbol=config;lines=32-34] [cite:file=src/strategy/bullish_trend_continuation.py;symbol=__init__;lines=24-37]. Specific strategies include `RSIMeanReversionStrategy`, which identifies entries when RSI(2) drops below a threshold in an uptrend [cite:file=src/strategy/rsi_mean_reversion.py;symbol=RSIMeanReversionStrategy;lines=14-229], and `ThreeDownDaysStrategy`, which buys after consecutive down closes to capture selling exhaustion [cite:file=src/strategy/three_down_days.py;symbol=ThreeDownDaysStrategy;lines=14-181]. Pattern-based strategies such as `BullishHaramiStrategy` and `BullishMarubozuStrategy` detect specific two-candle and single-candle formations, respectively, using configurable tolerance thresholds [cite:file=src/strategy/bullish_harami.py;symbol=BullishHaramiStrategy;lines=14-153] [cite:file=src/strategy/bullish_marubozu.py;symbol=BullishMarubozuStrategy;lines=14-134]. The base `Strategy` class exposes a `config` property to allow other components to access specific strategy settings [cite:file=src/strategy/strategy.py;symbol=config;lines=32-34] [cite:file=src/strategy/strategy.py;symbol=Strategy.config;lines=32-34].
*   **`src/data`**: The `CSVDataSource` class implements the `MarketDataSource` interface to read OHLCV data from local CSV files, supporting optional index and weight files for portfolio calculations [cite:file=src/data/market_data.py;symbol=CSVDataSource;lines=439-666]. The `get_candles` method abstracts file-based storage, returning a sorted list of `Candle` objects for a given symbol and date range [cite:file=src/data/market_data.py;symbol=get_candles;lines=563-581].
*   **Top-level Scripts**: `run_backtest.py` contains the `main` function that loads configuration, fetches index symbols, and initiates the simulation [cite:file=run_backtest.py;symbol=main;lines=24-93].

## 3. Notable functions/classes

The `BacktestEngine` class serves as the central orchestrator for the simulation loop, processing buy and sell signals while managing concurrent positions, stop-losses, and equity updates for each candle [cite:file=src/backtest/engine.py;symbol=BacktestEngine;lines=129-620]. This component is critical because it ensures that the financial state of the portfolio is accurately tracked over time, allowing for realistic performance evaluation of trading strategies [cite:file=src/backtest/engine.py;symbol=BacktestEngine;lines=129-620].

Configuration management begins with the `load_backtest_config` function, which validates the file path and parses data into a `BacktestConfig` object [cite:file=src/backtest/config_reader.py;symbol=load_backtest_config;lines=155-212]. This function acts as a factory, encapsulating the instantiation logic to ensure all required components are resolved before execution begins [cite:file=src/backtest/config_reader.py;symbol=load_backtest_config;lines=155-212]. The configuration is then passed to specific strategy implementations, such as `BullishTrendContinuationStrategy`, which accepts a `StrategyConfig` in its `__init__` method to define parameters like `trend_days` [cite:file=src/strategy/bullish_trend_continuation.py;symbol=__init__;lines=24-37] [cite:file=src/strategy/bullish_trend_continuation.py;symbol=BullishTrendContinuationStrategy.__init__;lines=24-37]. This abstraction supports the Strategy Pattern, allowing for interchangeable trading logic within the system [cite:file=src/strategy/strategy.py;symbol=config;lines=32-34] [cite:file=src/strategy/bullish_trend_continuation.py;symbol=__init__;lines=24-37]. ## 4. Data flow and design patterns

The backtesting workflow initiates when the `main` function in the entry point script receives a configuration path and calls `load_backtest_config` to parse the YAML file [cite:file=run_backtest.py;symbol=main;lines=24-93]. This function validates the file path and constructs a fully resolved `BacktestConfig` object, encapsulating the instantiation logic for the backtest components [cite:file=src/backtest/config_reader.py;symbol=load_backtest_config;lines=155-212]. The system then utilizes the **Factory/Builder** pattern to ensure all required components are resolved before execution [cite:file=src/backtest/config_reader.py;symbol=load_backtest_config;lines=155-212]. The configuration is passed to specific strategy implementations, such as `BullishTrendContinuationStrategy`, which accepts a `StrategyConfig` in its `__init__` method to define parameters like `trend_days` [cite:file=src/strategy/bullish_trend_continuation.py;symbol=__init__;lines=24-37] [cite:file=src/strategy/bullish_trend_continuation.py;symbol=BullishTrendContinuationStrategy.__init__;lines=24-37]. The strategy class exposes this configuration via a `config` property, allowing other components to access the strategy's specific settings [cite:file=src/strategy/strategy.py;symbol=config;lines=32-34] [cite:file=src/strategy/strategy.py;symbol=Strategy.config;lines=32-34].

During execution, the system employs the **Repository Pattern** in the data access layer, where the `get_candles` method abstracts file-based storage behind an interface that returns domain `Candle` objects [cite:file=src/data/market_data.py;symbol=get_candles;lines=563-581]. The `CSVDataSource` class implements the `MarketDataSource` interface to read OHLCV candle data from local CSV files [cite:file=src/data/market_data.py;symbol=CSVDataSource;lines=439-666]. These data points are processed by the strategy to generate signals, utilizing the **Strategy Pattern** where specific implementations like `BullishTrendContinuationStrategy` adhere to a common interface defined by the base `Strategy` class, allowing for interchangeable trading logic [cite:file=src/strategy/strategy.py;symbol=config;lines=32-34] [cite:file=src/strategy/bullish_trend_continuation.py;symbol=__init__;lines=24-37]. The `BacktestEngine` orchestrates the simulation loop, processing buy/sell signals and managing concurrent positions, stop-losses, and equity updates per candle [cite:file=src/backtest/engine.py;symbol=BacktestEngine;lines=129-620]. Upon completion, the `result_printer` module analyzes the output, with the `_parse_csv_result` function reading the CSV file to extract sections such as "BACKTEST CONFIG" and summary fields into a dictionary for reporting [cite:file=src/backtest/result_printer.py;symbol=_parse_csv_result;lines=92-117].
