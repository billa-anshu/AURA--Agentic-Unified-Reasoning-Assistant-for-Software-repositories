**End-to-End Data and Control Flow**

The system initiates the control flow through a stateless authentication mechanism. When a request arrives, the `AuthTokenFilter` intercepts it before it reaches the controller layer. This filter extends `OncePerRequestFilter` and utilizes the `parseJwt` method to extract the token from the `Authorization` header, specifically checking for the "Bearer " prefix [C19, C21]. The extracted token is then validated using `JwtUtils`, and the corresponding user details are loaded via `UserDetailsServiceImpl` to populate the `SecurityContext` [C19]. If authentication fails or the token is missing, the `AuthEntryPointJwt` component handles the exception by sending an unauthorized error response to the client [C28]. This entire security chain is orchestrated by the `WebSecurityConfig`, which defines the `SecurityFilterChain` and disables CSRF while enabling CORS for the frontend origin [C12, C23].

Once authenticated, the request proceeds to the REST controllers, which act as the entry point for business logic. For example, the `AuthController` handles login requests by delegating to the `AuthenticationManager`, which uses a `DaoAuthenticationProvider` to verify credentials against the `UserDetailsService` and a `BCryptPasswordEncoder` [C27, C24, C12]. For resource-specific operations, controllers like `PetController` and `AppointmentController` use method-level security annotations such as `@PreAuthorize` to enforce role-based access control (e.g., `hasAuthority('USER')`) [C25, C20]. Inside these methods, the current user's identity is retrieved from the `SecurityContextHolder` to determine the principal's ID, which is then used to scope data access [C25, C22].

The processing layer interacts with the data layer through Spring Data repositories. In `AppointmentController.bookAppointment`, the system validates the existence of the pet and doctor by calling `findById` on `petRepository` and `doctorRepository`, throwing a `RuntimeException` if entities are not found [C20]. Similarly, `PetController.getMyPets` filters data by calling `petRepository.findByOwnerId` using the ID extracted from the authenticated user details [C25, C26]. This pattern ensures that data retrieval is strictly scoped to the authenticated user's context, preventing unauthorized data access at the storage level.

On the client side, the frontend interacts with the backend through a centralized service layer. The `UserService` in `frontend/src/services/user.service.js` encapsulates all API interactions, providing methods like `getMyPets`, `addPet`, and `bookAppointment` that map directly to the backend's REST endpoints (e.g., `/pets`, `/appointments`) [C13, C14, C15]. This service layer abstracts the HTTP communication, allowing frontend components to consume data without managing raw API calls, thereby maintaining a clean separation between the UI and the network layer.

**Design Patterns**

The architecture prominently utilizes the **MVC (Model-View-Controller)** pattern, where `PetController` and `AppointmentController` serve as the controllers handling HTTP requests, while the frontend services act as the view layer's data access point [C26, C20, C13]. The **Repository Pattern** is evident in the use of `PetRepository` and `DoctorRepository` to abstract data persistence and retrieval logic, allowing controllers to interact with data without knowing the underlying database implementation [C20, C25]. Additionally, the **Filter Chain** pattern is implemented through the Spring Security configuration, where `AuthTokenFilter` acts as a middleware component in the request pipeline to handle authentication before the request reaches the controller [C19, C12]. Finally, the **Strategy Pattern** is implicitly used in the security configuration, where `DaoAuthenticationProvider` and `BCryptPasswordEncoder` are injected as beans to define the specific authentication and password encoding strategies [C24, C12].
