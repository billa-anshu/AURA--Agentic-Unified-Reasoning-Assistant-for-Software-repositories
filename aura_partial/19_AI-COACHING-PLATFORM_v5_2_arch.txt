The application initiates the user journey through a centralized authentication and user provisioning layer. The `AuthProvider` component wraps the application, utilizing the `useUser` hook to detect authenticated sessions. Upon detecting a user, it triggers the `createNewUser` callback, which executes the `api.users.CreateUser` mutation to persist user details such as name and email into the backend [C9]. This establishes the foundational user context required for subsequent interactions, ensuring that all downstream actions are associated with a specific user identity.

The primary entry point for creating a new interaction is the `UserInputDialog` component, which serves as the input interface for the user to select an expert and topic. When the user proceeds, the `onClickNext` handler invokes the `api.DiscussionRoom.CreateNewRoom` mutation via `useMutation` [C7]. This action generates a new discussion room, which is then navigated to using the router, effectively transitioning the control flow from the dashboard to the specific room view identified by the `roomid` parameter [C7].

Within the `DiscussionRoom` view, the system orchestrates real-time data retrieval and state management. The component uses `useQuery` to fetch existing room data and previous transcripts based on the `roomid` obtained from `useParams` [C2]. Simultaneously, it initializes state for the selected expert, microphone status, and current transcript text [C2]. This setup prepares the environment for real-time voice processing by establishing the necessary data context before any audio input is handled.

The core processing logic for voice interaction is handled by the `startListening` function, which leverages the Web Speech API. It checks for browser support, instantiates `webkitSpeechRecognition`, and configures it for continuous listening with interim results [C10]. As audio is processed, the `onresult` event handler updates the local `transcript` state with the recognized text [C10]. This raw text is then passed to the `AIModel` service, which constructs a prompt by replacing placeholders in a predefined coaching option template with the user's topic and message [C3]. The `AIModel` function sends this structured prompt to an external LLM endpoint (`deepseek/deepseek-chat-v3-0324:free`) to generate a response [C3].

Finally, the system provides multimodal output by converting the AI's text response into audio. The `speakResponse` function utilizes the `SpeechSynthesisUtterance` API to vocalize the generated text, handling specific language code mappings (e.g., mapping 'te-IN' to 'te') to ensure correct pronunciation [C13]. It also manages the speech synthesis lifecycle by canceling any ongoing speech before starting a new utterance [C13]. Throughout this flow, the application demonstrates a **Client-Side State Management** pattern using React hooks (`useState`, `useQuery`, `useMutation`) for data fetching and state updates [C2, C7, C9]. Additionally, it employs a **Service Layer** pattern, where business logic such as prompt construction and API calls is encapsulated in dedicated functions like `AIModel` and `startListening`, separating concerns from the UI components [C3, C10].
