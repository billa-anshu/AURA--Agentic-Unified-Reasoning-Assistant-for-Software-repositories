## 3. Notable functions/classes

The `encode_with_bpcs` function serves as the primary steganographic engine by converting input images into NumPy arrays and identifying complex regions within lower bit-planes to hide messages [C2]. It tracks embedding maps and conjugation details to ensure accurate data extraction later, which is critical for maintaining the integrity of the hidden payload [C2]. Complementing this, the `decode_with_bpcs` function extracts hidden messages by parsing a provided key to reconstruct the embedding map used during the encoding phase [C14]. It converts the stego image to a NumPy array and utilizes the map coordinates to retrieve the embedded data, completing the steganographic cycle [C14]. For legacy support, the `encode_to_image` function provides LSB encoding by converting messages to binary and embedding them into image pixels, including a capacity check that raises an error if the message exceeds the image's maximum storage limit [C13].

On the frontend, the `handleDecode` asynchronous function manages the decoding workflow by validating the presence of a cover image and decryption key before initiating the backend request [C12]. It reads the image file as a Base64 string and sends it to the server, providing real-time user feedback on the decoding status [C12]. Specifically for image-in-image scenarios, `handleImageInImageDecode` creates a canvas and uses a FileReader to process the uploaded stego image, initializing DOM elements and image loading events to prepare for bit-plane analysis [C11]. The `uploadImageToSupabase` utility handles data persistence by verifying the user's authentication session and constructing a unique file path using a timestamp and filename before uploading to Supabase Storage [C6]. The `handleUpload` method triggers this process by passing the selected file and a hardcoded email address, updating the UI status to reflect success or error states [C18].

Authentication is managed through several key functions. The `handleLogin` function simulates a successful login by setting the user state and notifying the parent component via the `onLoginSuccess` callback, then navigating to the `/app` route [C8]. Similarly, `handleSignup` handles user registration by simulating a successful signup and updating the local user state to navigate the user to the main interface [C16]. The `handleLogout` function clears the current user state by setting it to null, triggering a re-render of the login interface [C17]. In the `StegoApp` component, `handleSignup` interacts directly with `supabase.auth` to manage user sessions and store the user object in local state [C23]. The `PSNRAnalyzer` class initializes a Tkinter-based GUI for analyzing the Peak Signal-to-Noise Ratio of images, setting up the main window and frames for file selection and result viewing [C1]. Its `run` method starts the main event loop, making the window interactive and responsive to user input [C9, C10].

## 4. Data flow and design patterns

The application follows a Client-Side Routing and State Management pattern, where the `App` component acts as a controller that switches views based on authentication state [C4]. When a user logs in, the `handleLoginSuccess` function updates the `isAuthenticated` state, which triggers a navigation redirect to the main application route [C15]. This flow ensures that unauthenticated users are directed to the login screen, while authenticated users access protected features [C4].

For data ingestion, the system supports a specific upload pathway where the `UploadComponent` captures file input and invokes `handleUpload` [C18]. This function calls `uploadImageToSupabase`, passing the file and a hardcoded email string, which verifies the Supabase session and constructs a file path before initiating the storage upload [C6, C18]. This separation of concerns exemplifies the Service Layer pattern, where modules like `uploadToSupabase.js` encapsulate API interaction logic, allowing UI components to remain decoupled from specific implementation details [C6, C18].

On the backend, the Python application handles processing requests by extracting `image` and `message` fields from the JSON payload [C22]. The backend maintains in-memory state using a `stored_keys` dictionary and a `recent_operations` deque, which are explicitly commented as temporary solutions to be replaced by a database in production [C19, C20]. This demonstrates a Stateful In-Memory Storage pattern, indicating a prototype architecture that lacks persistent storage infrastructure [C19, C20]. Additionally, the `testDatabaseInsert` function verifies database connectivity and user authentication by retrieving the current Supabase user and attempting to log the result, serving as a diagnostic utility for the persistence layer [C3]. This function is executed upon component mount via the `runTestInsert` effect hook, which logs the result to the console to verify backend integration during initialization [C5].
