The application follows a standard Model-View-Controller (MVC) architecture where the `AdminController` serves as the entry point for HTTP requests. For instance, when a request is made to edit a classroom, the `editClassroom` method in the controller intercepts the GET request, extracts the `id` path variable, and prepares the necessary data for the view [C24]. Similarly, the `editTeacher` method handles requests to edit a teacher by retrieving the specific teacher and all available courses to populate the form [C22]. The controller layer does not contain business logic or direct database access; instead, it delegates all data retrieval and manipulation tasks to the service layer, specifically the `adminService` [C22, C23, C24].

The service layer, implemented by `AdminServiceImpl`, acts as the intermediary between the controller and the persistence layer. It exposes methods such as `getClassroomById`, `getAllCourses`, and `getAllTeachers` which are invoked by the controller to fetch data [C19, C20, C24]. In some cases, the service layer performs minimal processing, such as in `getCourseById`, where it uses `findById` and throws an `IllegalArgumentException` if the entity is not found, ensuring that the controller receives either a valid object or a clear error signal [C19]. The `editStudent` controller method demonstrates a slightly different flow where it retrieves all students via `adminService.getAllStudents()` and then uses Java Streams to filter for the specific student ID, indicating that the service layer provides bulk data retrieval which the controller then processes [C23].

Data persistence is handled through the Repository pattern, where the service layer interacts with Spring Data JPA repositories such as `courseRepo` and `classroomRepo`. Methods like `getAllCourses` and `getAllClassrooms` in `AdminServiceImpl` directly call `findAll()` on their respective repositories to retrieve lists of entities [C19, C20]. For individual entity retrieval, the service uses `findById()` which returns an `Optional`, a common pattern in Spring Data JPA to handle potential null values gracefully [C19, C21]. Deletion operations, such as `deleteCourse`, are also delegated directly to the repository's `deleteById` method, showing a direct pass-through of persistence commands from the service to the data layer [C19].

The design patterns evident in this codebase include the **MVC pattern**, where `AdminController` handles the request/response cycle and view resolution (e.g., returning `"classroom-form"`), while `AdminServiceImpl` handles the business logic [C22, C24]. The **Repository pattern** is clearly visible in the service layer's dependency on `courseRepo` and `classroomRepo` for all CRUD operations, abstracting the underlying database interactions [C19, C20]. Additionally, a form of **Facade pattern** can be observed in `AdminServiceImpl`, which aggregates access to multiple repositories (courses, classrooms, teachers, students) behind a single service interface, simplifying the controller's dependencies [C19, C20, C23].
